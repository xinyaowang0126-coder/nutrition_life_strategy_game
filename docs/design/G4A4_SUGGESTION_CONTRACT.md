# G4A4：当前候选、冷却与下一餐计划契约

2026-10-09。服务规则版本 `feasible-options-v2`，不改变组成模型 `diet-pattern-v2.0 / meal-composition-v1`、健康档案 schema、R2 或四个生产开关。

## 当前候选

`FeasibleSuggestionService.find_option(context, config, registry, date, copies, policy={})` 先复用组成/文案审核门，再从角色状态明确为 `not_recorded` 的角色中筛选全部可执行的加选或替换。`unknown` 不等同于缺少。

每个候选仍核对来源/餐次、当前手牌、完整组合快照、预算/费用、库存和数量上限，并保留所有已有明确角色。缺少蔬菜但当前来源找不到蔬菜时，继续检查其他可执行角色；不从水果或奶类推导蔬菜。

排序为：保留现选的加选优先 → 固定呈现顺序（蔬菜、蛋白质来源、主食）→ 总费用低者优先 → 同费用时可用显式角色口味 → ID 稳定排序。此顺序只是界面呈现策略，不是营养分数、个人摄入目标或医学严重程度。口味不改组成，也不能跨过可行性、角色或费用门。

最多返回一个 `action` 和一个折叠 `alternative`。备选需改变食物或加选/替换方式；不重复列同一食物的多个等效移除变体。两者均由 `MealGuidanceAdapter.resolve_proposal(..., policy={})` 重新计算和比对后解析成选择，原确认流程才付款、消耗库存和推进。`context_token`、`policy_token`、当日及服务版本参与完整动作比对。

## 可选策略输入

```text
policy.preferences   显式 FoodPreferenceService 角色档案；默认无偏好
policy.history       本局显示/拒绝回执；最多63条，严格类型/时序
policy.meal_history  确认时冻结的 MealHealthSnapshot；最多21餐，不能重复或包含当前/未来餐次
```

策略只读、返回独立副本，无文件写入或新存档。非法、未来或重复记录拒绝策略，而不静默跳过后放行。

## 冷却

`SuggestionMemory.record(history, action, event="shown")` 显式记录已显示或被拒绝的建议。调用 `find_option` 本身不记回执、不消费冷却，不让刷新页面不断换答案。

- 提示标识按角色、食物、来源分组；拒绝该食物后，不立即改成其加选/替换变体继续提示。
- 前两餐显示过的同标识进入冷却；当前餐仅拒绝回执进入冷却，已显示回执保持当前内容稳定。
- 优先选不在冷却中的其他候选。
- 全部候选冷却时，只有当前角色仍明确缺少、紧邻的前两顿都为已确认/已审核且明确缺少同一角色，才允许重复。显示回执、预览、跳餐、未知或未审核记录不能证明模式持续。

## 计划型回退

缺少可执行候选或全部候选冷却且不满足重复例外时，可返回 `plan_next_meal`：目标日/餐次/角色、`requires_recheck=true`、`executable_now=false`，食物ID空、来源空。它不是可点击的购买建议，不声明未来抽到哪些牌、多少钱或有多少库存。到下一餐时需用真实手牌重新计算。

第7天晚饭后没有下一餐，因此返回 `plan=null`。资料或文案未过门、角色未知或当前结构无需调整时也返回空，不生成泛泛计划。计划输出是结构化候选；正式玩家文案及UI接入仍待审核。开发预览只使用中性“午饭再看看配料”等短句。

## 本轮范围

完成当前加选/替换候选、稳定排序、一主一备、显式冷却与抽象下一餐计划。不提前抽牌、不换来源、不跨餐报价，不完成因素优先级、日/周聚合、正式生产UI或自动engine影子路径。测试中模拟审核不写回生产资料；23份profile仍draft。
