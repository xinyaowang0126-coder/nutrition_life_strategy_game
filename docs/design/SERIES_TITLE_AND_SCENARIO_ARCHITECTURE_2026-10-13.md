# 人物系列：游戏标题、故事入口与场景结构

日期：2026-10-13。状态：设计方案。依据用户确认的老年人物设计及后续人物系列方向；本轮调整产品文档与开发拆分，尚未更名运行项目或接入人物选择。

2026-10-14续接：已完成首个双故事可玩原型，当前实现与待细化内容见[实施记录](../process/SERIES_IMPLEMENTATION_2026-10-14.md)。以下保留设计时的完整方案与当时状态，不把原型工程完成等同专业或教育验收。

## 1. 系列名称与故事名称

**建议系列总名为《好好吃饭》，副标题为“营养科普生活策略游戏”。** 名称直接表达核心主题，也能容纳不同年龄、工作和生活目标。《撑过这一周》保留为学生篇标题，继续承接已经形成的校园生活内容。

系列工作名用于本方案；现有游戏窗口、主菜单与Web包仍显示《撑过这一周》。正式采用后，应在同一轮实现中更新运行项目、主菜单及导出页面，保持玩家看到的名称一致。源码文件夹、项目目录与已有历史文档不因名称调整而批量改名。

| 层级 | 建议内容 | 用途 |
| --- | --- | --- |
| 系列总名 | 好好吃饭 | 主菜单、窗口、发布页与系列介绍 |
| 系列副标题 | 营养科普生活策略游戏 | 说明玩法与教育属性 |
| 学生故事 | 撑过这一周 · 考试周 | 保留已有校园故事；专属目标为复习 |
| 周阿姨故事 | 自己的舞台 · 汇演周 | 66岁退休人物，七天后参加社区合唱汇演 |
| 后续故事示例 | 项目交付周、轮班的一周 | 仅作扩展例子，各自需要独立人物、课程和玩法设计 |

主菜单文字建议：

> **好好吃饭** <br>
> 营养科普生活策略游戏 <br>
> 选一个生活故事，安排三餐、日常任务和休息。 <br>
> [选择生活故事]

“离考试还有七天”“安排三餐、复习与休息”等校园文字移入学生故事的介绍。系列主菜单采用人物故事册或公共餐桌作为主题；学生头像和宿舍背景可继续用于学生卡及其故事页。

## 2. 人物、故事和地点是三层内容

| 层 | 回答的问题 | 学生示例 | 周阿姨示例 |
| --- | --- | --- | --- |
| 人物 | 谁在过这一周？ | 学生身份、口味、人物立绘 | 周慧兰，66岁，偏爱番茄炒蛋和蒸鱼，参加社区合唱 |
| 生活故事 | 这一周有什么目标和限制？ | 考试周，复习目标、预算、校园事件 | 汇演周，排练与实际参演、家庭预算、社区活动 |
| 地点与表现 | 当前在哪、能做什么？ | 宿舍、食堂、便利店、校园道路 | 家里厨房、小超市、社区食堂、排练室、舞台 |

人物决定身份、年龄及个人偏好；故事决定本局初始资源、任务、日程、食物可得性与学习主题；地点承接选择和美术表现。同一个人物以后可以有新的故事，不需要重新复制一份人物基础设定。

故事与人物通过显式支持关系绑定。退休人物的汇演周、学生的考试周先做为两张完整故事卡，不向玩家展示可任意搭配的两套下拉框。新增同人物的其他故事后，再在人物卡内展示可选择故事。

当前XML中的`scenes="breakfast,lunch,dinner"`指餐次／流程阶段，不能拿来承载新的故事ID。设计上区分`character_id`、`scenario_id`、`location_id`、`phase_id`；旧字段先保留兼容映射，避免全量改名引入回归。

## 3. 玩家入口与一次游玩的流程

```mermaid
flowchart LR
    A[系列主菜单] --> B[选择生活故事]
    B --> C[人物与本周目标]
    C --> D[开始这一周]
    D --> E[三餐与日常安排]
    E --> F[日结与次日]
    F --> E
    F --> G[故事结局与饮食回顾]
    G --> B
```

故事卡第一层显示人物、故事名称、目标、生活地点与预计时长；点击后用一页介绍预算、已有存货、来源开放、特殊机制和主要学习主题，再开始。资料详情可展开，不把开发字段或审核术语堆在普通玩家入口。

| 故事卡 | 本周目标 | 生活条件 | 主要学习机会 |
| --- | --- | --- | --- |
| 学生 · 撑过这一周 | 在考试前完成复习准备 | 校园食堂、外卖、便利店和宿舍存粮；学习与休息争用时间 | 组成与搭配、餐次规律、预算规划、资料边界 |
| 周阿姨 · 自己的舞台 | 周日完成社区合唱汇演 | 在家做饭、社区食堂、小超市和冰箱存粮；排练、采购与休息争用时间 | 老年营养、盐／钠、糖与标签、适口制作、剩菜食安 |

当前只有学生故事可玩。人物系列接入时，周阿姨达到工程与内容条件后再加入可开局列表；开发中的故事如需展示，明确显示“开发中”，不能点击后悄悄进入学生故事。

现有项目没有完整跨启动存档，入口暂不添加“继续上次”的功能承诺。结局提供“再玩这个故事”和“选择其他故事”；回到选择页后重新开局，不把上一局状态带给新人物。

## 4. 共用什么，按故事替换什么

| 共用层 | 内容 | 故事拥有的配置与规则 |
| --- | --- | --- |
| 日常流程 | 日期推进、选来源、选餐、确认、餐后行动、晚间安排、日结和结局入口 | 首轮两篇均为7天；阶段开放、日历文字和特殊事件各自配置 |
| 游戏资源 | 余额、精力、饱腹、心情、压力、余力及真实消费 | 初始值、采购价格、来源代价、行动代价和经验证的平衡参数 |
| 角色目标 | 目标标题、进度显示、记录与达成检查 | 学生复习；周阿姨排练及实际参演；未来可有阶段任务或里程碑 |
| 用餐组件 | 菜单、卡片、价格／库存、确认与记录 | 每个故事的来源、食品池、开放条件、选择上限和实际菜单 |
| 库存与制作能力 | 数量检查、消费一次、防重复确认 | 宿舍取存粮、家里消费原料做菜、冰箱熟食批次及再热，是不同能力 |
| 事件与预告 | 当日事件入口、效果说明、次日预告与触发记录 | 事件清单、日期／阶段、条件、影响和人物台词 |
| 科学教育 | 已知／估算／未知、证据与资料版本、冻结记录、观察与迁移任务 | 适用人群、教学主题和已复核资料；营养结论不能由角色名字自动推出 |
| 界面与美术 | HUD、弹窗、餐盘、桌面／竖屏布局结构 | 立绘、地图、地点背景、来源道具、活动插画、文案及结局图片 |

新人物的最低内容要求：一个自己的目标；至少一项有策略价值的生活限制；与现有章节有区别的来源／行动／事件；明确的营养学习机会；对应人物的结局与实际回顾。新图像和新台词不能单独算作新故事完成。

来源要区分“显示名称”与“操作能力”。宿舍存粮可以消费一件已备食品；家里做饭需要检查原料、消费配方所需数量、生成带版本和保存史的熟食份；冰箱取用需要核对批次和食安状态。仅将“宿舍存粮”改成“家里厨房”无法得到后两种玩法。

## 5. 开发数据与单局状态的边界

首轮继续沿用项目熟悉的XML配置、现有GDScript系统服务和场景组件，不因增加人物就全量更换数据格式或复制整个游戏控制器。

| 对象 | 应负责的内容 |
| --- | --- |
| 人物配置 | ID与版本、姓名与年龄、叙事背景、独立口味资料引用、人物美术、明确的个人进食条件 |
| 故事配置 | ID与版本、支持人物、天数、阶段结构、初始资源／库存、来源与行动池、事件表、任务与结局规则、课程引用、表现资源 |
| 已校验开局上下文 | 本局ID、人物与故事ID／版本、随机种子、玩法／课程版本，以及已解析的只读配置；开局前完成检查并冻结 |
| 单局状态 | 日期与阶段、当前资源、库存及熟食批次、目标进度／里程碑、已触发事件、当前选择和真实历史记录 |

主菜单只提交选择的故事身份。开局服务验证匹配的角色与故事，再把已校验上下文传给游戏控制器。控制器重开时使用本局的配置和新状态，而不是再次无条件读取默认校园人物。

采用一个小型开局交接服务即可；按人物分别增加全局单例没有必要。来源、目标和事件行为使用已实现且经过校验的能力类型，不从配置文本执行任意脚本。

### 5.1 通用目标接口

目标包含类型、显示名称、参考目标值、进度与额外达成事实。首轮支持两类：

- 学生：复习进度达到关卡目标，继续使用当前经验证的资源与结局条件。
- 周阿姨：排练达到关卡目标，在指定阶段满足游戏精力要求并实际参演；不能仅有进度条就声称登台成功。

HUD、行动、日结、恢复说明、余力计算和结局都读取同一目标上下文。“复习”不能只在HUD里改成“排练”，而底层仍校验学生的`study_progress`和结局文本。

当前余力公式将复习进度直接纳入贡献；迁移先通过显式校园适配保留现有行为，并为新目标定义受控的游戏进度贡献。不要在顺手改名时把原进度除以70再乘100，改变已验证的数值。营养评分继续独立，不能用盐糖参照或教育答题代替目标进度。

### 5.2 事件、地点与用餐来源

事件服务接收本局故事和日期／阶段，不再按全局固定表把“食堂换菜单”“小测提醒”应用给所有人。周阿姨的首日隔夜菜事件、周三／周五排练和周日演出属于她的故事表。

地点表现使用故事定义的桌面／竖屏资源。无专属插画时允许用同故事的中性场景；来源、任务或关键规则缺失时阻止该故事开局并显示可理解的原因，不能静默回退成校园玩法。营养数据未获批时保持未知与合法玩法，不从校园资料推断新菜的营养。

抽牌与可行建议使用当前故事的实际来源、食品池、开放条件、价格、手牌和库存。切换故事必须重新创建抽牌服务、选择缓存与建议上下文，不能继续复用上一局手牌。

### 5.3 记录与科学资料

新记录明确保存本局ID、人物／故事身份和版本、配方／标签及规则版本。查看历史使用确认时冻结的事实，不按照当前人物或新配方重解释过去的餐次。

已有历史格式通过明确的兼容路径继续显示，不批量重算或补写人物身份。缺失的故事元信息保留缺口；不能因为上一版只有学生，就把所有无身份外来记录默认认成学生。

完整存档需要另行设计，包括随机数、库存批次、阶段、触发去重和目标状态。现有健康历史JSON只能作为历史资料，不能冒充完整游戏存档。

## 6. 当前实现核对与具体迁移点

以下基于2026-10-13实际源码，描述要承接的工作，不代表已经完成。

| 文件／模块 | 当前校园绑定 | 需要迁移的边界 |
| --- | --- | --- |
| `project.godot`、主菜单场景与导出入口 | 窗口名《撑过这一周》；主菜单显示校园生活、考试七天与学生头像 | 系列名、公共入口、故事卡与专属介绍；命名变更和导出同步验证 |
| `MainMenu.gd`、`Boot.gd` | 启动主菜单，开始按钮直接进入`GameRootV2` | 增加故事选择与开局上下文；启动场景仍可复用 |
| `GameData.gd` | 固定初始资源、复习目标70及校园结局 | 从已校验故事读取配置，保留校园默认适配与既有测试入口 |
| `GameRootV2.gd`开局 | 无条件加载默认偏好、宿舍库存及校园事件 | 开局／重开按故事解析，彻底重建单局状态；不同故事之间无共享可变状态 |
| `GameRootV2.gd`表现 | 固定校园地图、宿舍背景、事件图片、学习图片 | 从当前故事的表现资源查找，兼顾竖屏资源和实际地点 |
| `MealSourceStage`与来源分发 | 依赖四个固定来源ID；未知来源默认走食堂 | 由受支持能力类型分发；新来源未实现时明确不可开局，不自动冒充食堂 |
| `WeeklyEventService.gd` | 第2–6天固定校园事件 | 接收故事事件清单，预告、应用和历史保存同源；保留触发一次 |
| `CharacterHUD.gd`、日结及结局 | 固定复习字段、文字和目标引用 | 显示通用目标与当前故事结果；回顾只消费实际记录 |
| `RecoveryGameplayService.gd`、`GameReserveCalculator.gd`及恢复记录 | 恢复效果／文案仍使用复习概念，验证固定7天；余力含复习进度 | 明确校园兼容和目标适配，保持R2已确认行为；新故事参数单独验证 |
| 科学资料与记录模块 | 资料／模型有版本和审核边界，正式输出仍待审校 | 新人群／配方／教学内容独立承接证据，开局上下文与历史身份同源 |

首轮两篇都维持7天。即使故事配置有天数字段，也不能宣称14天或30天已经支持；恢复校验、日期推进、结局、周带显示与统计均存在七日假设，需要另一个完整开发切片。

## 7. 分步实施与验收

| 顺序 | 交付 | 验收重点 |
| --- | --- | --- |
| SERIES-01 故事骨架与校园迁移 | 人物／故事配置、开局上下文、通用目标和来源／事件／表现查询；将现有学生故事接入 | 同种子、同预算下比对现有校园七日、失败和重开行为；资源、手牌、库存与冻结记录不能因抽取结构而无意改变 |
| SERIES-02 系列入口与名称 | 系列主菜单、故事卡、介绍页、结局返回；采用名称后同步项目和Web显示 | 桌面／竖屏实际阅读与点击；未完成故事不会误入校园；旧校园一键开局保留合法路径 |
| SERIES-03 周阿姨纵向切片 | 接入新目标、家庭／社区地点、原料制作、剩菜处置及教学标签 | 新人物能开局、过日、重开，目标没有校园文字；正确／不安全／未知保存路径正确；营养量不从名称补造 |
| SERIES-04 两篇完整验证 | 完成周阿姨七日与汇演、科学内容复核及试玩，验证来回切换两篇 | 学生→周阿姨→学生后人物、偏好、预算、库存、事件、随机数及记录均隔离；真实输入与教育迁移任务通过 |
| SERIES-05 后续故事 | 逐篇增加目标、现实限制、来源能力、课程和美术 | 可复用部分由配置接入；新行为单独实现和验证；每篇有独立科学与玩家验证记录 |

最低切换检查：新局不继承上一局余额或库存；重开保留当前故事；回到选择页不消费食物；预览不推进日期；任务／事件／演出不重复结算；旧历史按旧版本显示。

本轮只确定系列化设计、名称建议与迁移顺序。源码场景、窗口名、Web发布包与当前校园玩法未变；不能把文档中的目录和模块称为已经实现。
