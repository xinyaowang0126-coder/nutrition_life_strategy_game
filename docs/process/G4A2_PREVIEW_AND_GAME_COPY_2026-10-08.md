# G4A2：可操作的菜单预览与游戏文案

2026-10-08。按用户“像一个游戏正常会有的文案风格”的要求，完成隔离菜单/组成/日记预览、记录接口与当前手牌的可行加选/替换。测试菜单并非已审生产内容，正式营养输出保持关闭。

## 可以实际做什么

在Godot运行res://tests/preview/G4MealPreview.tscn。食堂试菜单有七项、每餐最多三样、预算¥20，依次安排早饭、午饭、晚饭。价格和配方是明确的测试设定，复用实际来源的开放时段、支付方式和数量上限校验。

- 点选时显示米饭/番茄/鸡蛋等已允许的原料；份量单独写“份量未标”，配料不全有自己的状态。
- “看配料”只展开说明，不收费、不确认、不改变记录。
- 当前手牌有可执行选项才显示“再加番茄·合计¥7”或具体替换。加选可负担时优先保留现选；买不起加选或已选满时检查替换。没有可行选项就不显示按钮。
- 只有“就吃这些”才扣费、冻结记录并进入下一餐。建议不是继续条件；不采用、跳过或改选都按同样规则推进。
- “今天吃了什么”列真实确认过的餐次，一次只显示一条事实。重复原料每餐只计一次，不把两张含鸡蛋的卡算成吃了两顿鸡蛋；未到晚饭时不补造记录。

新HealthGuidancePresenter提供只读meal_view、capture_record和diary_view；MealCompositionPanel为复用界面，来源/价格与健康快照分区。FeasibleSuggestionService只产生一个当前加选/替换动作，检查信息门、实际来源、阶段、数量、余额/服务费、库存、同日精确候选快照，并保留既有明确结构。执行前重算、核对revision，拒绝过时动作。

生产控制器未接这些模块，测试场景/fixture不进入Web包。NUT-305只完成当前上下文基础筛选，不是完整候选排序/冷却/下一餐规划服务；records是开发预览记录，不是新游戏存档或健康档案schema。

## 这次的文案取舍

| 原来的写法/问题 | 现在的呈现 |
| --- | --- |
| “这餐记录了……出现过不代表份量已经足够”每次附一段解释 | 主界面直接列“米饭·番茄·鸡蛋”，份量写成单独标签，解释在“看配料” |
| “这餐已有主食记录，其余配料还待核对” | 部分信息的短句为“能确认主食，其他配料没写全”；原料和“配料不全”一起呈现，避免重复朗读 |
| 不知道时仍称“这餐已经记下” | “配料还在核对”，可用于确认前预览，确认动作另行负责记录 |
| “这一餐跳过了。下次安排时，可以给吃饭留个空档” | “这顿没吃。” |
| 日结“给明天留出调整空间”等泛泛评价 | 只保留实际计划差额、低精力/余额和下一日事件；无事项时留空 |
| “今天吃了几餐，选过的食物记在下面”与上下布局矛盾 | 普通游戏日结按真实餐次写“午饭没吃”“今天三顿都吃了”等，不重复指挥读者 |
| 日结“写给明天”及重复恢复原因 | 标题“明天”；首层恢复档位+效果，原因仍可在详情查看 |

guidance_copy.xml的正向模板仍draft，审核/证据门未减弱；中性模板白名单同步。没有改成励志旁白、道德化食物评价或健康分。静态改写和截图尚不代表目标玩家觉得自然，真人复述/趣味验证仍待做。
