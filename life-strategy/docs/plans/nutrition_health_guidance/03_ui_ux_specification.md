# 03 营养与健康 UI/UX 规范

## 1. 目标

让玩家在“做选择时”看懂餐盘结构，在“回顾时”识别一天/一周模式；不把界面变成健康仪表盘，也不削弱预算、便利、口味和复习安排等游戏取舍。

本文件是现有 [V2 UI 重制计划](../../UI_REMAKE_PLAN.md) 的专项增量规范。背景、卡牌风格、主题、阶段场景和通用响应式规则仍以 V2 计划为准。

## 2. 信息层级

### 2.1 游戏优先门槛

营养与健康能力必须寄生在已有玩法世界里，而不是把游戏包进一张健康报告。玩家首层优先使用自然中文和已有游戏物件：**今日三餐、食物卡、餐盘、便签、角色状态、查看、选择**。以下规则是后续 UI 的硬门槛：

1. 自然中文优先；不得为了“显得像游戏”反复使用玩家不会自然说出的包装词。物件隐喻只在确实有对应交互时使用；
2. 首屏先回答“我这一局发生了什么、下一步能做什么”，再提供“依据是什么”；
3. 主标题和主按钮不得使用“健康评估、营养报告、饮食结构记录、指标、达标率、风险等级”等后台/报告词；
4. 不以四象限指标卡、环形图、仪表盘、绿黄红总览作为默认页面骨架；
5. 膳食指南名称、适用范围和免责声明只放在三餐详情末尾的一行“规则小字”或二级 `HealthInfoPanel`，不得成为视觉中心；
6. `draft / needs_review / unknown` 资料只能生成保守的卡牌线索，不能包装成权威判定；
7. 隐去正文后，页面仍应凭场景背景、纸张/便签材质、卡牌和游戏按钮被识别为本项目的一部分，而不是医疗或健身应用。

玩家可见词汇映射：

| 系统概念 | 首层游戏表达 | 二级说明可用表达 |
| --- | --- | --- |
| meal record | 今日三餐、三餐情况 | 餐次记录 |
| observation | 今日小记、今天出现 | 饮食结构观察 |
| action | 写给明天、下次可以试试 | 一般性行动建议 |
| evidence/scope | 规则小字 | 依据、版本、适用范围 |
| unknown | 卡牌没写清、先不盖章 | 信息不足/未知 |

### 2.2 出现时机

健康信息分六个时机出现：

| 时机 | 玩家问题 | 展示内容 | 不展示 |
| --- | --- | --- | --- |
| 卡牌扫视 | “这是什么、多少钱、游戏效果怎样？” | 名称、种类、价格/库存、核心游戏效果 | 总营养分、好坏标签、长文 |
| 卡牌详情 | “这份食物大致包含什么？” | 份量基准、组成、做法、需留意因素、依据状态 | 个体处方、疾病结论 |
| 已选餐盘 | “我当前这一餐有哪些组成？” | 主食/蔬菜/蛋白质来源的实时预览 | “均衡/不均衡”判分 |
| 餐后短反馈 | “刚才这次选择记录到了什么？” | 一条结构事实，必要时一条未知提示 | 分数、惩罚、长篇建议 |
| 日结 | “今天三餐吃了什么、有没有没吃？” | 早餐/午餐/晚餐、今日小记、一条可行动提示；饮水/睡眠待独立轨道接入 | 指标看板、总分、排名、等级 |
| 周结 | “这一周哪些模式重复？” | 趋势、重复、数据缺口和回顾 | 健康人格评价、诊断 |

默认界面保持游戏优先；健康详情随时可访问，但不通过警报色或弹窗强迫玩家阅读。

## 4. 用餐选择界面

### 4.1 桌面布局

```text
┌────────────────────────────────────────────────────────────────────┐
│ 第 3 天 · 午餐              现金 / 余力 / 角色健康（游戏）          │
├───────────────┬───────────────────────────────────┬────────────────┤
│ 场景与来源     │ 可选食物                          │ 这餐已选       │
│               │ ┌──────────┐ ┌──────────┐         │ 主食   [有记录]│
│ 食堂窗口插画   │ │ 白米饭   │ │ 番茄     │         │ 蔬菜   [少量]  │
│               │ │ ¥2  饱腹 │ │ ¥3  心情 │         │ 蛋白质 [未记录]│
│               │ │ [i]      │ │ [i]      │         │                │
│               │ └──────────┘ └──────────┘         │ 已选：米饭、番茄│
│               │ ┌──────────┐ ┌──────────┐         │ [查看依据]      │
│               │ │ 鸡蛋     │ │ 青菜     │         │                │
│               │ └──────────┘ └──────────┘         │ [确认这一餐]    │
├───────────────┴───────────────────────────────────┴────────────────┤
│ 游戏提示：还可选 1 份 · 当前花费 ¥5                                │
└────────────────────────────────────────────────────────────────────┘
```

规则：

- 右侧 `PlatePreviewPanel` 只聚合已选卡，不给总分。
- “未记录”是本次选择状态，不是“缺乏”或“失败”。
- 复合菜按资料状态展示：固定游戏配方写“游戏内设定”，一般配方推算才写“估算”，未知则写“配方未明确”；三种状态都提供依据入口。
- 卡牌选中/取消时，预览在 150–250 ms 内更新，避免闪烁。
- 确认按钮仍由游戏选择规则控制；健康结构不作为强制通行条件。
- 玩家可以确认任何合法组合，包括跳餐；系统记录而不羞辱。

│ └──────────────────────┘ │

│ 这餐已选：主食有记录 · 蔬菜有记录│

- 预览和确认区固定在安全区底部，高度不超过可视区域约 28%。
- 点击 `[i]` 打开底部抽屉；不能依赖悬停。
- 最小触控目标 48×48 px，卡片内相邻按钮至少留 8 px。
- 在 `366×768`、`390×844` 和规划基线 `720×1280` 下验证。
- 系统字体放大到 130% 时，底部区域可增高或转为可滚动，不截断按钮。

## 5. 卡牌信息设计

### 5.1 卡牌正面

保留：

- 食物名称；
- `kind` 的简短种类标签；
- 价格/库存；
- 最关键的 1–2 个游戏效果；
- 信息按钮和选中状态。

可选增加：

- 最多 3 个小型组成图标，且只表示“资料中包含”，不显示完成勾；
- 低置信度时加“估算”小标，不用问号制造恐慌。

禁止：

- 0–100 分、星级、A/B/C；
- 绿色勾代表“健康”、红色叉代表“不健康”；
- “轻食=好、炸物=坏”的颜色编码；
- 把 `mood` 正负值放进饮食组成区。

### 5.2 详情便签

`StickyNotePopup` 目标结构：

```text
┌───────────────────────────────┐
│ 鸡肉时蔬饭               [关闭]│
│ 一份 480 g                      │
├───────────────────────────────┤
│ 游戏效果                       │
│ ¥22 · 饱腹 +28 · 余力 +9       │
│ 角色健康 -3（仅用于游戏结算）   │
├───────────────────────────────┤
│ 饮食信息                       │
│ 主食：熟白米饭 200 g             │
│ 蔬菜：三种，共 150 g             │
│ 蛋白质来源：鸡肉 100 g           │
│ 钠：尚未分类                    │
│ [查看完整原料]                  │
│ [信息依据与适用范围]            │
└───────────────────────────────┘
```

区块规则：

- “游戏效果”永远明确标为游戏数值。
- “饮食信息”来自 profile 和 Presenter，不从 `tags` 猜测。
- `display_basis` 和 `DataConfidenceBadge` 属 Presenter 输入；内部枚举只在审校/依据视图保留，玩家卡片只显示经过取舍的自然短语。
- `menu_recipe / package_label` 的确定值在数据和审校层保留“游戏内固定配方 / 游戏内模拟标签”；玩家界面优先写“一份 480 g”“便利店小杯”“包装上写着”。虚构商品、现实适用范围和膳食指南边界在一次性帮助/说明中交代，不在每张卡重复贴“游戏内设定”，也不能把界面伪装成真实品牌标签。
- draft profile 可以中性展示“一杯 350 ml”等已经冻结且对选择有用的世界内事实；咖啡因数值是否值得在当前情境展示由 Presenter 决定，factor 等级、晚间时机和行动建议只有通过对应规则与审核后才能显示。
- 有做法/需留意因素时与组成并列，不用扣分语言。
- 过敏原和食品安全信息只有在专用 schema、解析、校验和审核全部落地后才进入可展开区；明确食安事件届时可提升到首屏。当前空数组/空字典绝不能渲染成“无过敏原/无需冷藏/安全”。
- draft 但已有固定规格时，可显示原始份量、原料和做法，并把尚未通过规则审核的因素写成“尚未分类”；真正缺少配方资料时才写“配方未明确”。两者都不能写成“暂无风险”。

NUT-204C/D 的健康范围只完成数据、证据边界与校验，不新增当前玩家可见的健康面板或组件；NUT-204D 仅另行同步一处不含健康判断的酸奶生活描述。上述固定配方/包装商品详情、组成展开和状态文案在 NUT-402/403 接入；接入前不得把 draft 资料转成健康结论。

#### NUT-207 已接入的角色口味区（2026-09-04）

- V2 紧凑卡使用现有次要指标展示“口味 -2 / +3 / 0”，外卖行将饱腹和口味分两行；缺失偏好显示“口味未设置”。
- 食物详情在一般游戏指标之后单列“角色口味（游戏效果）”，例如“不太合本局角色的口味 · 心情 -2”。原 mood 不再混入一般食物指标格。
- 角色偏爱、合口味、没有特别偏好和未设置分别表达，不从糖、盐、油炸、食物组或健康资料推断口味。旧版卡片摘要和 tooltip 使用相同输入。
- 数据只来自 `payload.food_preference`；显示不回读食物 mood。V2 偏好更新后刷新卡面/详情，确认用餐按当前角色偏好重新计算，已确认记录保持原样。
- 行动、来源和睡眠的心情仍为原有游戏效果。此改动不代表健康资料 Presenter、组成预览或 M4 健康详情已落地。
- 专项 UI 测试 9/9 通过；1920×1080 桌面与 720×1280 竖屏的青菜、沙拉碗、修改口味三种实际渲染均通过，见测试文档 5.5。详情先按宽度刷新换行、重测高度再定位；旧异步显隐回调失效，避免换卡或关闭时复开详情。

### 5.3 包装商品小档案

NUT-204D 为未来 UI 冻结以下呈现契约，本轮不修改生产 `StickyNotePopup`、不新增健康面板或组件；唯一玩家可见同步是把酸奶卡牌生活描述改得更自然，且不承载健康结论：

```text
┌───────────────────────────────┐
│ 原味酸奶                  ¥6  │
│ 便利店小杯 · 180 g             │
├───────────────────────────────┤
│ 游戏效果                       │
│ 饱腹 +7 · 余力 +4 · 心情 +4    │
├───────────────────────────────┤
│ 商品小档案                     │
│ 一杯 180 g · 微甜               │
│ [翻到包装背面]                  │
└───────────────────────────────┘
```

交互和文案规则：

- 卡牌正面仍优先呈现名称、价格、库存和游戏效果，不增加“高钙/高纤/健康选择”等徽章。
- 包装商品详情使用 `[翻到包装背面]`、`[看看包装]` 或同义的世界内动作，不把主按钮写成“查看模拟标签/查看健康报告”。
- 第一层“商品小档案”只挑选玩家此刻容易理解、确实有用的自然事实：牛奶为一盒 250 ml；原味酸奶为一杯 180 g、味道微甜；全麦面包为两片共 70 g。数据存在不等于必须全部露出，不能把详情做成内部数据检查器。
- `confidence=high / review_status=draft / package_label / factor band` 等内部治理字段不直接露出，也不在每张卡加“游戏内设定”元话语；draft 阶段不显示“低糖/高糖、低钠/高钠、足够/达标”等解释。虚构规格与现实边界集中放在首次帮助和二级依据页。
- 发酵乳基底 172 g、添加糖 8 g，以及各条目的 `not_applicable / baked`、confidence、review 和 band 默认保留在内部规格与审校视图。只有 NUT-505 把某项定义为可信、适合教学的包装字段后，Presenter 才可按情境选择性展示；即使届时展示，牛奶的“未添加糖”也不能改写成“无糖”，酸奶和面包的糖/钠信息也不能由 UI 自行上色或下结论。
- 本区不是完整营养成分表。每 100 g/ml、每份换算、`NRV%`、标准版本和同类商品比较全部留给 NUT-505；在它们落地前，不绘制仿真的法规标签表格。
- 过敏原、冷藏、保质期和开封后处理不从原料名或卡牌描述推断。过敏原字段由后续 schema 切片承接，冷链/过期事件由 NUT-506 承接；未实现时不显示空的“安全”结论。
- 未来接入时须同时检查卡图、单位名词和生活描述是否一致。例如牛奶卡面当前画的是杯装牛奶，而文案写“一盒”；若保留盒装商品规格，应在视觉资产任务中统一，而不是让详情同时说“杯”和“盒”。

## 6. 餐盘预览组件

### 6.1 内容

`PlatePreviewPanel` 默认显示三类单餐结构：

| 角色 | 状态文案 | 视觉 |
| --- | --- | --- |
| 主食/谷薯 | 有记录 / 少量记录 / 未记录 / 信息不足 | 图标 + 文字 + 纹理 |
| 蔬菜 | 同上 | 图标 + 文字 + 纹理 |
| 蛋白质来源 | 同上 | 图标 + 文字 + 纹理 |

水果、奶类、坚果只在“今日记录”小行中出现，不伪装成每餐必选位。

### 6.2 交互

- 新选卡：对应组成轻微淡入，并在卡牌与预览之间做一次短暂关联高亮。
- 取消卡：重新计算聚合状态，不做红色损失动画。
- 复合菜：点击组成可展开具体原料；未知原料显示“配方未明确”。
- 键盘焦点到卡牌时，可在预览中显示“若选择”的虚线变化；移开后恢复。
- 触屏不使用悬停预览，选中后再更新；卡牌信息按钮用于先看详情。
- 动画遵循系统“减少动态效果”设置，可完全关闭。

## 7. 餐后短反馈

确认一餐后使用现有 `ToastFeedV2` 或场景内便签，最多两行：

正例：

- “这餐记录到主食、蔬菜和蛋白质来源；份量以卡牌资料为准。”
- “这餐有主食和蛋白质来源记录，蔬菜组成未记录。”
- “方便面的钠信息值得查看；它仍提供了主食组成。”

不使用：

- “本餐 86 分”“完美餐盘”“吃得很差”；
- “炸鸡抵消了青菜”“喝水清零负担”；
- 餐后立即弹出多个行动建议。

如果需要建议，餐后只提供“查看三餐详情”入口；主要建议在日结或下一次选择时出现。

## 8. 每日总结

### 8.1 页面结构

现有 `DailySummaryPopup` 改为以下顺序：

1. **收工标题与游戏结算**：余力、复习、余额仍是主要游戏反馈；
2. **今日三餐**：早餐、午餐、晚餐各一格，写来源和最多两项食物；没吃则直接显示“没吃”；
3. **今日小记**：一条克制、自然的本局观察，例如“今天有一餐没吃”；不做等级或总评；
4. **写给明天**：先给一条可执行选择，再接复习/预算和明日事件提示；
5. **查看三餐详情**：展开三餐情况、卡牌线索和规则小字；
6. **继续按钮**：使用“睡到第 N 天”等世界内动作。

```text
┌──────────────────────────────────────────────┐
│ 第 3 天，收工                                 │
│ 余力 64        复习 30/70        余额 ¥82      │
├──────────────────────────────────────────────┤
│                  今日三餐                     │
│ ┌─────────┐ ┌─────────┐ ┌─────────┐          │
│ │ 早餐    │ │ 午餐    │ │ 晚餐    │          │
│ │食堂·饭蛋│ │便利店·苹果│ │没吃     │          │
│ └─────────┘ └─────────┘ └─────────┘          │
│                                              │
│ ┌ 今日小记 ────────────────────────────────┐ │
│ │ 今天有一餐没吃。先把这件事记下来。         │ │
│ ├ 写给明天 ────────────────────────────────┤ │
│ │ 明天要是排得开，先给吃饭留个空档。         │ │
│ └──────────────────────────────────────────┘ │
│                                              │
│ [查看三餐详情]               [睡到第 4 天]      │
└──────────────────────────────────────────────┘
```

### 8.2 三餐概览与详情

- 三餐格只复述玩家实际选择，不推断份量是否充足；三种颜色可区分时间段，但颜色不表示好坏。
- 桌面横排三格，窄于 `430px` 时纵向排列；没吃/缺失使用灰底和文字双重区分。
- 首层不显示“四维卡片”。未来四维评估器输出被转译为一条今日小记；完整维度只在三餐详情中按事实展开。
- 详情标题使用“本局线索”，可列三餐情况、餐盘线索、卡牌资料线索和需留意的卡牌线索。
- 详情末尾最多一段规则小字；完整机构、版本、链接和特殊需求说明留在二级 `HealthInfoPanel`。
- 饮水与睡眠在数据模型、评估和视觉上都保持独立；在对应任务完成前，不强行塞入本日营养结论，也不接入暂缓的混合“角色健康”指标。

每餐最多显示两项食物，更多项用“等”收口。默认首屏只保留一条值得记住的观察和一条下一步。

### 8.3 无建议状态

当没有必要或没有可行建议时：

> “今天的三餐先记到这里。明天仍可以照预算、时间和口味来选。”

不要为了保持卡片有内容而生成泛化“多吃蔬菜、多喝水”。

## 9. 每周回顾

`WeeklyPatternRecap` 在第 7 天或结局前呈现，不改变结局判定：

```text
一周饮食记录
餐次       一 二 三 四 五 六 日
早餐       ● ● — ● ? ● ●
蔬菜记录   — ● ● — ? ● ●
油炸做法   — — ● — — — ●
饮水事件   2  1  3  0  ?  2  2
睡眠选择   早 中 晚 晚 ?  中 中

本周看到的模式
• 午餐比晚餐更常出现蔬菜组成。
• 鸡肉时蔬饭重复 3 次，按同一套固定原料去重。
• 两次晚餐含油炸做法；这些记录没有被其他选择抵消。
```

图例必须解释：

- `●` 有记录；
- `—` 未记录；
- `?` 信息不足。

不使用热力图“越绿越健康”的默认语义；玩家可逐日展开查看原始选择。

## 10. 健康信息与依据面板

`HealthInfoPanel` 从主菜单、卡牌详情和日/周总结均可进入，包含：

1. **这套反馈做什么**：帮助观察一般饮食结构和生活记录；
2. **不做什么**：不诊断、不处方、不替代专业医疗服务；
3. **信息如何产生**：卡牌配方/标签 → 结构规则 → 受控文案；
4. **数据状态**：明确、估算、未知分别是什么意思；
5. **主要依据**：标题、机构、适用范围、版本和链接；
6. **遇到特殊需求**：提示向合格专业人员咨询，不收集具体病史。

面板不展示内部权重，因为目标模型没有总分；可以展示每条观察使用的规则和证据 ID。

该面板始终是玩家主动打开的二级页面。日结首层只允许出现一行“规则小字”，示例：

> 规则小字：本局饮食信息参考《中国居民膳食指南（2022）》的一般原则；卡牌出现不代表现实摄入量足够，也不用于现实健康判断。

除法规/专业复核要求的必要声明外，不在首层重复机构、证据编号、模型版本或长免责声明。

## 11. 文案映射

| 当前/风险表达 | 目标表达 |
| --- | --- |
| 营养评分 / 今日饮食结构记录 | 今日小记 / 今日三餐 |
| 餐盘完整 | 主食、蔬菜和蛋白质来源均有记录（份量以资料为准） |
| 优先补齐蔬菜 | 下一餐可考虑加入当前可选的蔬菜 |
| 营养表现差 | 今天有一餐没吃 / 有些卡牌没写清 |
| 高分食物 | 不使用；分别描述组成和需留意因素 |
| 清零/抵消身体负担 | 角色健康上升（游戏效果）；不改变饮食记录或饮食观察 |
| 脑雾 | 进入状态较慢（游戏效果） |
| 自律/放纵 | 具体描述预算、口味、便利和选择 |
| 喝够水 | 记录到饮水行动（容量未知时） |

健康文案必须来自 `guidance_copy.xml` 的已审核 `copy_id`；UI 代码不得硬编码同义句。

## 12. 视觉语义

### 12.1 游戏物件语言

- 日结主体使用有折痕/阴影的纸张、手写便签和轻量卡片等材质，与宿舍和餐桌场景呼应；
- 饮食线索采用卡牌图标、餐盘槽位或食材贴纸，不使用医院十字、心电图、体检报告表格；
- 展开详情仍停留在同一张日结便签中，而不是切换到分析仪表盘；
- 动画只强化物件感：三餐格依次出现、便签轻微缩放、详情展开；关闭动画后信息与顺序不变；
- 代码中的 `health_*` token 仅是实现名，不直接成为玩家标签。

### 12.2 状态色

建议在 `V2Theme.tres` 中新增语义色 token：

| Token | 建议色相 | 用途 |
| --- | --- | --- |
| `health_recorded` | 蓝绿/青色 | 有记录，不代表“优秀” |
| `health_partial` | 沙金色 | 有但不完整 |
| `health_attention` | 赭黄/琥珀 | 值得留意，不使用危险红 |
| `health_unknown` | 中性灰蓝 | 信息不足 |
| `health_safety_alert` | 低饱和红 | 仅明确食品安全阻断事件 |

同时使用形状和文字：

- 有记录：实心圆 + “有记录”；
- 部分：半圆/点状纹理 + “少量/不完整”；
- 留意：菱形 + “值得留意”；
- 未知：虚线圆 + “信息不足”。

### 12.3 图标

- 图标描述食物组或信息状态，不画体重秤、腰围、红叉食物。
- 油炸/添加糖/钠使用事实图标，不使用骷髅、警笛或火焰惩罚。
- 组成图标需有文本替代；不能要求玩家只认图。

## 13. 无障碍与输入

- 正文最小视觉字号建议 16 px；关键状态 18 px；可随系统缩放。
- 正文与背景对比至少满足 WCAG AA；文字不直接压在复杂背景上。
- 所有组成、因素和置信度都有可读文本。
- 焦点顺序：阶段标题 → 来源/卡牌 → 信息按钮 → 餐盘预览 → 确认。
- 弹窗打开后焦点进入标题/关闭按钮；关闭后返回触发控件。
- `Escape/返回` 先关闭详情，不直接丢弃本餐选择。
- 触屏按钮最小 48×48 px；键盘焦点有 2 px 以上高对比描边。
- 支持减少动态效果；关键内容不依赖动画出现。
- 长文依据面板可滚动，并保留关闭按钮。

## 14. 数据与失败状态

| 状态 | UI 行为 |
| --- | --- |
| profile 缺失 | 显示“这张卡的饮食资料尚未补齐”，游戏选择仍可继续 |
| 引擎失败 | 隐藏建议，显示“本次结构记录暂不可用”，不要回退到旧分数 |
| 证据过期 | 该观察降级为未知/保守文案，并记录开发警告 |
| 候选卡变化 | 重新验证建议；失效建议立即撤下 |
| 旧存档 | 显示“历史记录信息不足”，不重算伪结果 |
| 多模型版本 | 周回顾按版本分段或只展示原始选择 |

## 15. UI 遥测原则

只记录改进交互所需的匿名事件：

- 是否打开饮食信息详情；
- 是否理解数据状态的任务测试结果；
- 建议是否可点击/因何被过滤；
- 页面溢出、焦点失败和异常。

不记录现实疾病、体重、过敏史、饮食障碍、真实摄入或可识别个人资料。不要把玩家是否接受建议作为“健康顺从度”评分。

## 16. 分阶段 UI 落地

### UI-0 文案安全修正

- 删除日结“营养评分”标题和数字。
- 内部 `burden` 以“角色健康”正向展示并标注“游戏属性”；不得进入健康指导区。
- 把“餐盘完整”等绝对结论改为“组成有记录”。

### UI-1A 日结游戏外壳（已实施）

- 保留游戏结算，接入“今日三餐”、今日小记和“写给明天”。
- 详情沿用同一张日结便签，依据压缩为一行规则小字。
- 桌面三列、窄屏单列，详情滚动不遮挡继续按钮。
- 本阶段只改玩家呈现，不声称新四维评估器或专业审核内容已上线。

### UI-1B 日结正式健康输出（随 NUT-404）

- 用新评估器/Presenter 替换过渡 `NutritionLedger` 文案，继续复用三餐概览外壳。
- 每日只挑一条值得记住且有依据的观察，不把四维结果铺成首屏指标卡。
- 饮水、睡眠等独立轨道仅在各自数据和评估任务完成后接入。

### UI-2 选择期反馈

- 新增 `PlatePreviewPanel`。
- 详情便签拆分游戏效果与饮食信息。
- 完成桌面/竖屏布局。

### UI-3 周回顾

- 增加七日轨迹和详情展开。
- 独立展示饮水/睡眠。
- 用户测试确认没有被理解为评分。

## 17. UI 验收标准

- [ ] 玩家在不打开长说明时，可说出当前餐盘记录到哪些组成。
- [ ] 健康指导区域没有总分、食物好坏等级或抵消语言；“角色健康”只出现在明确的游戏属性/游戏效果区域。
- [ ] 卡牌仍能清楚表达价格、库存和游戏效果，健康信息没有压过玩法。
- [ ] 隐去正文后，日结截图仍可凭三餐卡片、便签、游戏统计和继续动作被识别为游戏界面，而不是健康报告。
- [ ] 膳食指南与免责声明只在规则小字/二级依据页出现，不占主标题、首屏卡片或主按钮。
- [ ] 一条建议能点击定位到实际候选卡/来源；失效后不会继续显示。
- [ ] 桌面和竖屏下预览、确认、关闭和滚动均可用。
- [ ] 仅看灰度、使用色觉模拟或关闭动画时仍可辨识状态。
- [ ] profile 缺失、引擎失败、旧存档和证据过期都有安全降级态。
- [ ] 日结和周结没有用颜色、图形面积或顺序暗示隐藏总分。
- [ ] 5 名以上目标玩家测试中，多数不会把“有记录”理解成“已经达标”。
