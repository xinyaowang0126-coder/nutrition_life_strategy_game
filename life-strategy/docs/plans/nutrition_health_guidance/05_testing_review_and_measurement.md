# 05 测试、专业审校与效果评估

## 1. 目标

证明新系统同时满足四件事：

1. **计算正确**：同一输入稳定，复合菜、重复、未知和边界状态处理一致；
2. **表达安全**：没有总分、抵消、诊断、伪精确或道德化；
3. **建议可执行**：与真实来源、预算、库存和阶段一致；
4. **玩家能理解**：能区分游戏效果与饮食信息，并把观察迁移到下一次选择。

自动化测试不能代替营养专业审校；专业审校也不能代替组合、布局和存档测试。

## 4. 数据层测试

### 4.1 正常加载

- 23 个 `food_id` 可连接到 profile 或允许的缺失白名单；
- 根版本、profile 版本和模型版本正确读取；
- component 和 factor 子节点完整解析；allergen、food safety 仍是后续 schema/解析任务，当前空占位不得被测试或 UI 解释为“无过敏原/无储存要求”；
- 逗号列表去空白、去空项，但不静默修复非法枚举；
- 重新加载同一文件结果稳定。

### 4.2 阻断错误

逐一构造：

- 重复/不存在 food_id；
- 负份量、value 无 unit、unit 无 value；
- 未知枚举；
- 已知且同单位的 component 总量不等于已知份量；
- 跨 profile 复用同一 ingredient_id 却改变 food_group；
- expert_reviewed 缺证据或复核日期；
- factor 的 none/high 无依据；
- `deep_fried` 使用 low/moderate/high，或做法与 present factor 未双向匹配；
- `not_applicable` 与任何其他 cooking method 共存，或把它用于推断无需冷藏/没有食品安全要求；
- 证据 ID 不存在/已失效；
- 引用集合不具备调用方声明的 required capabilities；
- 复合菜 component 为空且没有 unknown；
- 不支持的 schema 版本。

断言错误包含文件、food_id、字段路径和可操作说明。

### 4.3 未知传播

- 缺 profile → unknown，不回读旧 `food_groups`；
- unknown portion → 不能生成“足量/达标”；
- unknown factor → 不能变成 none；
- low confidence 复合菜 → 餐盘结果最多 partial；
- 草稿资料 → 只能使用保守文案。

## 8. 文案安全测试

### 8.1 静态 lint

对健康模板扫描：

- 禁止词：`排毒、燃脂、治愈、预防疾病、清零、自律失败、垃圾食物、罪恶`；
- 谨慎词：`必须、一定、导致、缺乏、过量、达标、健康/不健康`，出现即要求人工豁免；
- 每条模板必须有 scope、evidence_refs、review_status；
- 插值变量必须在白名单；
- 健康模板不得包含游戏字段名或数值占位符；
- “足量/推荐量”只有在目标人群和可靠数量都明确时才允许。

静态扫描不能判断全部语境，仍需逐条人工审校。

### 8.2 结构断言

- observation title/detail 不包含总分或等级；
- 游戏效果区必须带“游戏”标签；
- unknown 状态只能使用 unknown 类 copy_id；
- 一个建议最多一个主动作；
- 无建议时有中性空态，不自动补泛化建议。

## 11. 流程、存档和回退测试

以下包含新系统最终验收目标。NUT-206 已实现的范围为 [5.4 独立健康历史](#54-nut-206-快照与独立健康历史验证记录)，其载入接口不提供完整游戏状态恢复，也不接入历史展示 UI。

- 新游戏在开关 off/on 时均可完成七天；
- 开关 off 时玩家结果与冻结基线一致；
- 旧存档无 profile 快照时可加载并显示历史未知；
- 新存档保存 profile/model 版本，重载结果稳定；
- 一周内模型版本变化时按规则分段；
- UI 组件失败不阻断游戏结算；
- 回退开关不丢失现金、库存、复习和事件状态；
- 旧 `quality` 字段停止写入后，读取器仍能忽略旧值；
- 最终删除旧路径前，至少两个发布候选版本无回退需求。

## 12. 专业审校

### 12.1 审校包

每轮提供：

- 本方案和变更摘要；
- 23 个 profile 的差异；
- 证据登记与过期状态；
- 全部健康 copy_id；
- 15 个金样例的结构化输入/输出；
- 桌面与移动截图；
- 已知限制和未解决问题；
- 需要明确签署的决定清单。

### 12.2 必须角色

- 营养专业人员：饮食结构、份量表达、因素和建议；
- 食品标签法规熟悉人员：标签玩法和标准版本；
- 产品/叙事：非道德化、非诊疗和校园语境；
- UI/无障碍：信息层级、颜色、焦点和触控；
- QA/工程：规则与实现一致。

### 12.3 缺陷等级

| 等级 | 示例 | 发布处理 |
| --- | --- | --- |
| S0 严重 | 诊断/治疗建议、错误法规、明确危险食安建议 | 立即阻断，关闭功能 |
| S1 高 | 总分复现、抵消逻辑、把 unknown 当安全、建议不可执行 | 阻断发布 |
| S2 中 | 置信度不清、易被理解为达标、移动端重要信息隐藏 | 发布前修复或书面豁免 |
| S3 低 | 用词、间距、次要说明 | 可进入有期限 backlog |

S0/S1 必须为 0；S2 豁免需要专业和产品共同签字并设到期日。

## 13. 玩家理解与可用性测试

### 13.1 形成性试验

建议每轮 5–8 名目标玩家，至少两轮；发布前再做 10–15 名小型验证。它用于发现误解，不宣称医学效果或统计代表性。

任务：

1. 在食堂组合一餐并解释餐盘预览；
2. 比较炸鸡、沙拉、复合饭时说出“多面特征”，不选唯一健康答案；
3. 识别“估算/未知”是什么意思；
4. 在预算不足和来源受限时理解为什么建议变化；
5. 日结后复述一条今天的模式和一条可行动下一步；
6. 周结后说明为何没有总分。

观察问题：

- 玩家是否把“有记录”理解成“已经吃够”；
- 是否认为喝水/散步能抵消饮食因素；
- 是否认为游戏结局是现实健康诊断；
- 健康信息是否让预算和口味选择显得“错误”；
- 是否能在移动端找到依据和关闭详情。

### 13.2 暂定发布门槛

- 至少 80% 参与者能正确区分游戏效果与饮食信息；
- 至少 80% 能解释为什么系统没有总分；
- 至少 80% 能正确理解 unknown 不等于 none；
- 100% 测试中出现的主要建议都可在界面完成或被明确识别为下一餐计划；
- 0 个参与者在引导后仍认为系统给出了疾病诊断；
- 首两餐学习后，选择用时中位数相对旧版增加不超过 20%；
- 任一关键误解若重复出现于 2 人及以上，视为设计问题，不用增加免责声明掩盖。

这些是产品可用性门槛，可根据首轮基线调整，但降低安全门槛必须记录理由。

### 13.3 教育迁移与趣味验证（2026-10-08补充）

项目当前以营养科普教育为主要目的，同时保证趣味性。13.1–13.2的界面理解、未知态和可行性门仍适用，还需按[项目开发目标第6节](../../../../docs/design/PROJECT_GOALS.md#6-同时验证学习与乐趣)验证L1–L4和游玩意愿；只完成理解测试或健康详情不能证明教育候选完成。

- EDU-01的[七日场景与评分方案](../../../../docs/education/EDU01_LEARNING_SCENARIOS_AND_ASSESSMENT.md)和[参与者A/B任务页](../../../../docs/education/EDU01_PARTICIPANT_TASKS.md)已于2026-10-08准备，包含4组同难度的新菜单前后任务；玩家接入、专业签署和真人数据仍待后续。报告前后表现与人数，不把通关或某类食物选择率当学习成绩。
- 候选暂定至少80%参与者能在新菜单中解释组成与记录边界，并提出可行调整；同时沿用unknown、游戏效果、无诊断与无抵消要求。前测已有明显高分时改进任务，避免把原有知识算作游戏效果。
- 试玩记录首日独立完成、卡点、整局时长、5级兴趣和自愿再次尝试；暂定至少80%独立完成首日、兴趣中位数4/5、至少60%无额外奖励时愿意再试且能说出一项安排变化。预留复玩时间，未观察到实际行为时分开记录意愿和行为。
- 两轮每轮5–8人用于找问题，修订后10–15人验证候选；小样本用具体人数报告，不外推总体留存或医学效果。后续若要宣称教育效果，另设计对照与延后验证。
- 趣味与时长阈值可据首轮基线调整并记录理由；专业、证据和关键误导门槛保持。学习或乐趣任一未达到均继续修订，不能以另一方面的通过替代。

本节为计划补充，不代表已有真人数据、新引擎输出或专业签署。

## 14. 效果指标与隐私

优先指标：

- 结构信息理解正确率；
- unknown/estimated 的理解正确率；
- 建议可执行率；
- 从日结到下一餐能否应用同一判断；
- 详情打开后的任务完成率；
- 布局/焦点/退出失败率。

只作描述、不作成功 KPI：

- 玩家选择某类食物的比例；
- 建议接受率；
- 健康详情打开率。

这些行为不能用于判断玩家现实健康、自律或顺从度。不得收集体重、疾病、真实过敏史、真实摄入等敏感信息。

## 15. CI 与手动验证

从 `life-strategy` 目录运行完整测试：

```powershell
godot --headless --path . --script res://tests/headless_runner.gd
```

运行证据生命周期审计（默认使用 UTC 系统日期）：

```powershell
godot --headless --path . --script res://tests/evidence_audit_runner.gd
```

本地复现可追加 `-- --as-of=YYYY-MM-DD`。审计以单行 `HEALTH_EVIDENCE_AUDIT=<json>` 输出每条 `review_due_at`、下一复核日、待复核和已到期 ID；结构错误或存在到期记录时返回非零退出码。`needs_review` 会明确报告但不因其仅存在于登记册而让整个 CI 失败，具体引用检查仍会将其判为不可用于玩家指导。

发布候选还需：

- 启动 `res://scenes/game_v2/GameRootV2.tscn` 烟雾测试；
- 执行五个分辨率布局测试；
- 运行所有来源/餐次组合；
- 保存截图并由 UI/内容/专业人员抽检；
- 记录 Godot 版本、模型版本、证据版本和测试计数。

若本机使用自定义 Godot 可执行文件，CI 文档写清路径注入方式，不把个人绝对路径提交到项目。
